# Polymarket WSS 大规模订阅压测与性能优化方案

## 1. 文档目的与边界

本文用于规划 Polymarket Market WebSocket 在 **218,634 个 asset ID** 规模下的渐进式订阅压测、瓶颈归因与生产化容量设计。

边界如下：

- 客户端技术栈：Java 21、Spring Boot、OkHttp WebSocket。
- 本文只定义实验方案与优化路线，不把尚未执行的实验写成结论。
- Polymarket 官方目前**未公布明确的单连接订阅数或连接数硬限制**。实验中出现 close、failure、静默或吞吐平台，均只能表述为特定客户端、网络、时间窗口和服务状态下的观测，不能直接认定为官方上限。
- `book` 消息当前不能通过服务端订阅参数过滤；若订阅产生 `book`，客户端必须接收其网络流量。客户端可以不入业务队列，但不能节省已经发生的下行带宽和 WebSocket 解帧成本。
- 不以压垮服务端为目标。实验应在受控窗口逐级升压，并保留随时停止能力。

| 客户端 | Spring Boot + OkHttp |

| 已验证订阅级别 | 100 / 500 / 1,000，均稳定 |

| P3 `book` | 16 frames、465,620 bytes |

以上基线只证明 1,000 订阅在该次实验条件下稳定，不能外推 5,000—200,000 的表现。

### 2.2 10,000 Token 的 1013 现场与当前结论

两轮单连接 10,000 Token 均发生重连，因此不能判定为稳定容量。第二轮成功保留了服务端 Close：

```text
code=1013
reason=slow consumer: send buffer full
```

#### 关闭现场

- generation=1 于 22:14:20.952 建立，100 Token/批、250 ms/批加载订阅；约 22:14:47 完成 10,000 Token。
- 22:14:56 统计窗口为 987.9 frames/s、642,850.5 bytes/s；业务队列仅 1/10,000，dropped=0，onMessage P99=50 μs。
- 服务端于 22:15:02.997 主动发送 1013 Close，即全量订阅完成约 16 秒后关闭。
- 最后一次已记录 PONG 为 22:14:48.361，距离 Close 约 14.6 秒。10 秒采样粒度不足以判断是心跳响应本身延迟，还是 Close 帧在客户端读路径中排队。
- 76.8 ms 最大回调在首个统计窗口、约 2,000 Token 时已经出现，之后只是累计最大值；它与 Close 时刻没有可证明的时间相关性。
- 22:14:20.231 之后至 Close 前没有 Young/Full GC；Close 附近只有几十微秒级 Cleanup safepoint，因此 GC 不支持作为直接诱因。
- generation=2 约 1.8 秒后建立，使用相同批大小和批间隔恢复 10,000 Token，随后稳定运行到实验结束。这表明“10,000 Token”或“250 ms 批间隔”都不是每次必然触发的硬阈值。

#### send buffer 的语义

- 1013 在 IANA 注册语义为 `Try Again Later`，表示服务端因临时条件拒绝继续处理；具体 reason 是 Polymarket 的应用级诊断。
- 结合数据方向和措辞，`send buffer` 高概率指 **Polymarket 服务端向该客户端发送消息的单连接下行缓冲/队列**，不是 Java `ArrayBlockingQueue`，也不是 OkHttp `WebSocket.queueSize()` 所表示的客户端上行发送队列。
- “服务端发送缓冲满”是直接关闭原因，但不是最终根因。瞬时推送洪峰、客户端 Socket 读取短暂停顿、TCP receive window 收缩、网络重传、服务端节点瞬时过载或缓冲阈值偏小，都可能使该缓冲无法及时排空。
- OkHttp 的 WebSocket 读循环同步调用 `listener.onMessage()`；回调未返回时不能继续读取下一帧。因此回调阻塞理论上能够间接填满服务端发送缓冲。但本轮 P99、队列、CPU 和 GC 数据只排除了持续饱和，尚不能排除亚秒级读停顿。
- Polymarket 官方文档未公开单连接订阅硬上限、slow-consumer 判定窗口或发送缓冲大小。第三方给出的 200/500 等数字只能作为工程经验，不能作为官方限制。

#### 根因分级

| 级别 | 假设 | 当前判断 |
|---|---|---|
| 已证明 | 服务端单连接下行发送缓冲无法继续排空，并主动发出 1013 | 直接原因确定 |
| 高概率 | 订阅加载期的瞬时推送、资产活跃度与服务端节点/缓冲状态共同触发 | 符合 R2 时序，但 generation=2 同速恢复成功，不能归因于单一订阅速率 |
| 可能 | OkHttp 读线程短暂停顿或 TCP 接收窗口/重传异常 | 机制成立，但当前没有精确时间戳和 TCP 数据 |
| 证据不足 | Polymarket 存在固定 10,000 Token 限制 | 同配置重连后稳定，不支持硬上限结论 |
| 基本排除 | Java 业务队列持续积压、消费者长期不足、CPU 饱和、Full GC、关闭前 GC pause | 队列、dropped、CPU 和 GC 证据均不支持 |

#### 根因验证顺序

在增加连接数前，固定为单连接 10,000 Token，每组至少重复 3 次：

1. 基线复现：100 Token/批、250 ms/批。
2. 仅降低加载速度：100/500 ms、100/1000 ms、50/500 ms。
3. 固定速率比较 5,000、7,500、10,000，且保持同一组 Token 与相同测试时段，减少资产活跃度偏差。
4. 增加 100 ms/1 s 滚动窗口，记录 frames、bytes、book bytes、最大 Frame、回调最大值及其时间戳、inter-frame gap、PONG 往返时间、generation 和 close history。
5. 同步采集 JFR 与 Windows TCP 指标（重传、RTT、接收窗口）；若环境允许，再用抓包确认 Zero Window、重传和 Close 前的数据方向。
6. 增加纯计数模式：非 book 不跨线程持有完整 payload，用于排除对象保留和队列交接的影响。

判定规则：若降低订阅速度能在重复实验中稳定消除 1013，优先归因为加载期洪峰；若稳态仍随机出现，则重点转向资产热点、网络窗口、读线程停顿和服务端节点阈值。完成这些对照后，再决定多连接分片容量。

### 2.3 三个不可混用的统计量纲

| 量纲 | 定义 | 主要用途 | 常见误判 |
|---|---|---|---|
| frame | 一次 WebSocket 消息回调收到的完整文本或二进制消息 | 网络吞吐、最大帧、回调耗时、解帧压力 | 把 1 个 frame 当成 1 个业务事件 |
| event | frame 内的一个业务事件对象；数组 frame 可能包含多个 event | 业务处理速率、事件类型分布、积压判断 | 仅扫描一个 `event_type` 就推断 frame 内 event 数量 |
| token（asset） | 一个订阅 asset ID | 订阅规模、连接分片与覆盖率 | 用 token 数直接推算流量；不同 token 活跃度差异可能很大 |

后续报告必须同时记录 `tokens/connection`、`frames/s`、`events/s`、`bytes/s`。若当前实现尚未精确拆分数组中的 event 数，应将该列标记为“未采集”，不可用 frame 数代替。

## 3. 问题定义：何时才是 slow consumer

目标不是寻找一个孤立的“最大订阅数字”，而是回答：在给定硬件、JVM、网络、事件活跃度和业务处理成本下，客户端能否持续接收、分类、排队和消费全部有效事件，并保留足够容量余量。

### 3.1 因果链

典型 slow consumer 因果链如下：

1. 入站 `bytes/s`、`frames/s` 或 `events/s` 超过回调与消费者的持续处理能力；
2. OkHttp 回调执行时间升高，或业务队列 `enqueued - processed` 差值扩大；
3. 队列深度持续上升，且在稳定流量或停止升压后不能回落；
4. 队列到达容量，`offer()` 失败，`dropped` 增加；
5. 回调、GC 或 CPU 饱和进一步延迟 PING/PONG 和读循环；
6. 可能出现 PONG 变旧、发送队列增加、超时、异常 close/failure 或重连；
7. 重连后全量重订阅造成额外发送和初始快照流量，形成“重连—流量尖峰—再次失败”的正反馈。

只有单一信号不足以下结论。例如队列瞬时上涨后快速回落不是持续积压；无消息也可能只是市场不活跃，而不是服务端拒绝订阅。

### 3.2 slow consumer 判定原则

满足以下组合信号时，才判为“客户端消费不足的强证据”：

- 在不少于 3 个连续采样窗口内，队列斜率持续为正，且升压停止后仍不能回落；
- `enqueued - processed` 持续扩大，或 `dropped > 0`；
- `onMessage` p95/p99、CPU 或 GC pause 同时恶化；
- 增加消费者、减少模拟处理耗时或跳过业务解析后，现象显著缓解；
- 同期网络质量正常，且服务端 close/failure 没有在低客户端负载下同样发生。

## 4. 当前架构与线程模型

### 4.1 数据路径

```text
asset 文件加载
    │
    ▼
阶段控制线程 ──> 计算目标与分片 ──> 每连接订阅发送线程 ──> OkHttp WebSocket
                                                            │
                                                            ▼
                                                OkHttp onMessage 回调线程
                                                            │
                                      ┌─────────────────────┴────────────────────┐
                                      │                                          │
                              book：统计后丢弃                         非 book：offer()
                                                                                 │
                                                                                 ▼
                                                                  每连接有界 ArrayBlockingQueue
                                                                                 │
                                                                                 ▼
                                                                       业务消费者线程池
```

### 4.2 线程与资源职责

| 组件 | 当前模型 | 压测关注点 |
|---|---|---|
| OkHttp WebSocket | OkHttp Dispatcher/读回调线程 | `onMessage` 不应阻塞；文本帧已形成 `String`，二进制帧当前会 `utf8()` 转换 |
| 阶段控制 | 单线程 `benchmark-phase` | 按阶段设置总 token 目标与等待阶段时长 |
| 订阅发送 | 固定线程池，线程数等于连接数 | 按批发送，观察 `WebSocket.queueSize()` 和发送失败 |
| 调度器 | 2 个线程 | PING 与重连退避 |
| 入站队列 | 每连接一个 `ArrayBlockingQueue`，默认容量 10,000 | `offer()` 非阻塞；满时计 drop，避免阻塞 OkHttp 回调 |
| 消费者 | 固定线程池，默认 4 个；轮询各连接队列 | 公平性、空轮询成本、单热点分片、处理能力 |
| 指标/报告 | 原子计数、直方桶、阶段快照 | 指标本身的分配、竞争与日志开销 |

当前实现对 `book` 只统计、不进入业务队列；非 `book` 将包含原始文本的 `MessageEnvelope` 入队。这一设计保护业务队列，但 `book` 仍消耗网络、UTF-8/String 表示、类型扫描和指标更新资源。

## 5. 指标体系与判断标准

### 5.1 每阶段必采指标

| 层次 | 指标 | 建议统计 |
|---|---|---|
| 订阅 | 目标 token、已提交 token、连接数、每连接 token、批大小/间隔、订阅完成时间 | 总量及逐连接 |
| 入站 frame | frames、frames/s、bytes、bytes/s、KB/s、frames/KB、平均/最大 frame size | 总量及逐连接，至少 10 秒窗口 |
| event | events、events/s、event type 分布、unknown/mixed 数 | 若无法精确计数，明确标记未采集 |
| `book` | book frames、book bytes、占总 frames/bytes 比例 | 总量及逐连接 |
| 回调 | `onMessage` avg/p95/p99/max | 逐连接 |
| 队列 | depth、capacity、usage、峰值、增长斜率、enqueued、processed、dropped | 逐连接与总量 |
| 连接 | open、close code/reason、failure、重连次数、最近 PONG 年龄、发送 queueSize | 逐连接 |
| JVM | 进程 CPU、堆/非堆、分配率、Young/Old GC 次数和 pause、线程数 | 进程级；必要时 JFR |
| OS/网络 | 主机 CPU、RSS、网卡 bytes/s、丢包/重传、RTT、DNS/TLS/握手异常 | 主机与链路级 |
| 业务 | 端到端处理时延、有效事件处理率、数据新鲜度 | 若业务链路已接入 |

口径约定：`bytes/s` 始终表示每秒原始字节数；周期日志沿用需求中的 `KB/s` 标签，但明确按 `KB/s = bytes/s / 1024` 计算，即此处 `1 KB = 1024 bytes`。周期日志的 `frames/KB` 使用同一采样窗口计算，即 `窗口 frames / (窗口 bytes / 1024)`，窗口 bytes 为 0 时记为 0。最终 JSON/CSV 为避免二进制/十进制前缀歧义，阶段快照使用阶段累计量：`kibibytes = 累计 bytes / 1024`，`framesPerKiB`（CSV 为 `frames_per_kib`）等于 `累计 frames / kibibytes`，累计 bytes 为 0 时记为 0；它们不是速率指标，也不应与十进制 KB（1000 bytes）混用。

### 5.2 阶段结果分级

阈值应在实验前冻结，避免事后选择。推荐初始门槛如下，可依据业务 SLO 调整：

| 结果 | 判断标准 |
|---|---|
| PASS | `dropped=0`；无异常 close/failure；队列峰值 `<50%` 且阶段尾部能回落；PONG 持续更新；CPU、GC、内存无持续恶化；订阅全部提交 |
| WARN | 无 drop，但队列峰值 `50%—80%`、尾部未充分回落，或 CPU/GC/回调 p99 接近预算；允许复测，不允许直接升入生产容量 |
| FAIL | 任一 `dropped>0`；队列持续增长或 `>=80%`；订阅未完整提交；异常 close/failure/反复重连；PONG 超过预设超时；OOM、长时间 Full GC；网络安全阈值超限 |
| INCONCLUSIVE | 市场事件过少、网络异常、主机受其他负载干扰、服务端行为不一致或指标缺失，无法归因 |

“无 drop”不等于稳定：若测试结束早于队列填满时间，仍可能存在正积压斜率。

## 6. 实验前置与控制变量

1. 固定主机规格、JDK/JVM 参数、OkHttp 配置、队列容量、消费者数、asset 顺序、订阅 level、分片算法及日志级别。
2. 使用同一份 218,634 ID 清单并记录文件哈希；每个级别取其固定前缀，确保跨轮可比。
3. 记录实验日期、时段、网络出口、主机独占情况。市场活跃度不可控，因此至少重复多轮，并比较 `bytes/s`、`events/s`，不能只比较 token 数。
4. 每轮前确认 JVM 已启动稳定、监控可用、磁盘空间充足，且没有上一轮遗留连接。
5. 每次只改变一个主变量：单连接矩阵只改变 token；分片矩阵固定总 token 为 200,000，只改变连接数。
6. 先在低规模执行冒烟；任何高规模公网实验均需明确授权与维护窗口。本文不执行公网测试。

## 7. 第一阶段：单连接上限实验

### 7.1 实验矩阵

所有级别使用 1 条连接，目标订阅分别为：

| 级别 | 总 token | token/连接 | 建议稳定观测时长 | 最少有效重复 | 初始批次策略 |
|---:|---:|---:|---:|---|
| S1 | 5,000 | 5,000 | 10 分钟 | 3 轮 | 100/批，250 ms 间隔 |
| S2 | 10,000 | 10,000 | 15 分钟 | 3 轮 | 沿用上一级通过参数 |
| S3 | 20,000 | 20,000 | 20 分钟 | 3 轮 | 沿用上一级通过参数 |
| S4 | 50,000 | 50,000 | 30 分钟 | 3 轮 | 沿用上一级通过参数 |
| S5 | 100,000 | 100,000 | 45 分钟 | 3 轮 | 沿用上一级通过参数 |
| S6 | 150,000 | 150,000 | 60 分钟 | 3 轮 | 沿用上一级通过参数 |
| S7 | 200,000 | 200,000 | 60 分钟 | 3 轮 | 沿用上一级通过参数 |

“稳定观测时长”从**该级订阅全部提交且订阅发送队列恢复稳定后**开始计时，不把升压时间混入稳态窗口。高等级应至少覆盖一个相对活跃时段；若 `events/s` 过低，则结果为 INCONCLUSIVE，并应换时段复测，而不是延长到无边界。

### 7.2 升压与批次策略

- 每轮先以 1,000 token 冒烟 5 分钟，确认指标链路和网络正常。
- 同一条连接只做单向增量订阅时，阶段间保留 5 分钟冷静窗口；若不能取消订阅，则每一正式重复轮都新建连接，从零订阅到目标，避免继承状态污染。
- 初始使用现有 100 token/批、250 ms 间隔。不要在首次上限探索中同时扩大批次。
- 若订阅发送 `queueSize()` 持续上升、发送失败或连接在升压期间关闭，先降低发送速率（例如保持批大小、增大间隔）；只有在低速发送仍复现后，才把它记为该规模的连接/服务端候选限制。
- 一个级别必须 3 轮均 PASS 才升下一级；出现 1 次 WARN 则同参数补测；出现 FAIL 立即停止向上升压并进入归因。
- 找到首个 FAIL 后，可在“最后 PASS—首个 FAIL”之间增加二分点，但仍须遵守停止条件和重复规则。

### 7.3 单轮停止条件

任一条件触发即停止继续发送订阅，保存现场指标，并正常关闭可用连接：

- `dropped > 0`；
- 任一队列使用率 `>=80%` 持续 30 秒，或队列深度连续 3 个采样窗口增长且预计将在安全窗口内填满；
- 异常 close/failure，或同一连接在 5 分钟内重连 2 次；
- PONG 年龄超过 `max(3 × pingInterval, 30s)`；
- OkHttp 发送 `queueSize()` 连续增长且不回落，或 `send()` 返回 false；
- 进程 CPU 持续超过预设主机预算（建议实验前按核数定义，例如保留至少 20% 余量）；
- GC pause、堆占用或分配率触发实验前定义的安全阈值，出现 Full GC 抖动或 OOM 风险；
- 网络丢包/重传或带宽触达出口安全阈值；
- 服务端或平台明确要求降载，或观察到可能影响他人的异常。

## 8. 第二阶段：固定 200,000 token 的连接分片实验

仅在较低规模已验证客户端监控和停止机制后进行。若单连接尚未安全到达 200,000，可从已验证的多连接拓扑直接开始，但不得把它与单连接结果混为一谈。

### 8.1 分片矩阵

| 级别 | 总 token | 连接数 | 理论 token/连接 | 建议稳定观测时长 | 最少有效重复 |
|---:|---:|---:|---:|---:|---:|
| C1 | 200,000 | 16 | 12,500 | 30 分钟（仅诊断） | 1 轮 |
| C2 | 200,000 | 24 | 8,334 | 45 分钟（仅诊断） | 1 轮 |
| C3 | 200,000 | 32 | 6,250 | 60 分钟 | 3 轮 |
| C4 | 200,000 | 40 | 5,000 | 60 分钟 | 3 轮 |
| C5 | 200,000 | 50 | 4,000 | 60 分钟 | 3 轮 |

已有单连接 10,000 Token 的 1013 现场后，不再把 2/4/8 条连接、每连接 25,000—100,000 Token 作为默认生产候选。生产优先验证 4,000—5,000 Token/连接；16/24/32 档仅用于建立单连接容量曲线，不通过时立即转向 40/50 条连接。

默认采用稳定的 ROUND_ROBIN 分片，以稀释 ID 顺序与热点聚集影响；另选 4 或 8 连接做一次 CONTIGUOUS 对照，以识别资产排序造成的热点。每轮都记录实际每连接 token 数和流量偏斜，不能只记录平均值。

### 8.2 升压策略

1. 连接创建采用错峰，例如每 1—2 秒建立一条，避免瞬时握手尖峰。
2. 每条连接内部仍以 100 token/批、250 ms 间隔为初始参数；不同连接的批次发送增加少量抖动，避免同步尖峰。
3. 总订阅数可按 25% → 50% → 75% → 100% 四个台阶加载；每台阶至少观察 5 分钟并通过停止条件。
4. 连接数按 2×5,000 → 4×5,000 → 8×5,000 验证单 Worker 扩展性，再按 16/24/32/40/50 条连接验证总量；达到单 Worker 资源或稳定性阈值后改为多节点，不继续硬顶单进程。更多连接并非天然更好，会增加线程调度、TLS/TCP 状态、心跳、服务端连接配额和重连风暴风险。
5. 每个连接数级别从全新进程或完全清理后的连接状态开始，保证堆、队列与累计指标不串轮。
6. 停止条件沿用单连接实验，并增加：同一分钟内异常连接比例达到 10%，或逐连接流量极端偏斜导致单分片队列进入 WARN/FAIL。

## 9. 瓶颈归因

### 9.1 对照实验法

| 假设 | 典型证据 | 验证动作 | 支持该假设的结果 |
|---|---|---|---|
| 客户端 CPU/解析瓶颈 | CPU 高、回调 p99 高、分配率/GC 高、队列增长 | 同流量下跳过完整解析/业务处理；增加消费者；采集 JFR | 简化处理后队列和延迟显著改善 |
| 客户端消费者不足 | 回调正常，队列增长，`enqueued-processed` 扩大 | 消费者数 4→8 对照，业务处理改为空操作 | 增加消费能力后恢复稳定 |
| 客户端单连接读路径瓶颈 | 单连接失败，多连接总量相同却稳定，网络/CPU仍有余量 | 固定 200k 比较 2/4/8/...连接 | 分片后每连接回调/队列显著改善 |
| 服务端候选限制 | 客户端资源低、网络正常，但到固定 token/连接后可重复 close、拒绝或静默 | 降低订阅发送速率；换客户端主机/时段复测；保留 close/reason | 多环境在相近 token/连接复现，且客户端未饱和；仍只能称候选限制 |
| 网络瓶颈 | 重传/丢包/RTT 上升、吞吐触顶，多个应用同时受影响 | 同主机网络监控、换受控出口、比较 bytes/s 与链路容量 | 换健康链路后问题消失 |
| 市场低活跃 | token 很多但 events/s/bytes/s 很低，无异常 | 换活跃时段或采用历史已知热点集合做对照 | 高活跃窗口才暴露积压；原结果标记 INCONCLUSIVE |
| 订阅发送过快 | 升压期间 queueSize 增大/close，稳态尚未开始 | 减小批次或增大间隔 | 降速后相同 token 可稳定 |

### 9.2 决策树

```text
出现 drop、积压、close/failure、静默或吞吐异常？
├─ 否
│  ├─ 流量足够覆盖目标负载窗口？
│  │  ├─ 是 → 本轮 PASS/WARN，按余量判断是否升压
│  │  └─ 否 → INCONCLUSIVE，换活跃时段复测
│  └─ 不得据此宣称官方硬上限
└─ 是
   ├─ 主机 CPU/GC/内存/回调时延是否同步恶化？
   │  ├─ 是 → 简化解析/业务处理、调整消费者后复测
   │  │  ├─ 明显改善 → 客户端瓶颈
   │  │  └─ 无改善 → 继续检查网络与连接维度
   │  └─ 否
   ├─ 丢包/重传/RTT/出口带宽是否异常？
   │  ├─ 是 → 网络问题；换健康链路复测
   │  └─ 否
   ├─ 降低订阅批次速率后是否恢复？
   │  ├─ 是 → 订阅发送节奏问题
   │  └─ 否
   ├─ 相同总 token 增加连接分片后是否恢复？
   │  ├─ 是 → 单连接路径或候选每连接限制；继续跨环境复测
   │  └─ 否 → 总流量/客户端总容量或候选账户/出口级限制
   └─ 客户端有充足余量且跨主机、时段可重复？
      ├─ 是 → 记录为“服务端候选限制”，不宣称官方硬限制
      └─ 否 → INCONCLUSIVE，补齐证据
```

## 10. 性能优化路线

原则：先测量、后优化；每次只改变一类因素，使用相同输入规模和相近流量窗口做 A/B。队列扩容只能延长耗尽时间，不能修复长期消费速率不足。

### 10.1 P0：正确性与可观测性

1. 补齐逐连接重连次数、订阅完成耗时、PONG 年龄、发送 `queueSize()`、窗口速率和队列增长斜率。
2. 明确 frame/event/token 三套计数；数组 frame 需要低分配的 event 计数策略，无法可靠计数时标记缺失。
3. 记录实验配置、资产文件哈希、主机/JVM信息与停止原因，使结果可复现。
4. 校验 218,634 ID 的去重数、分片覆盖率和交集，避免把缺订阅误判为服务端静默。

### 10.2 P1：JVM 与 GC

- 固定 `-Xms` 与 `-Xmx`，避免压测期间扩堆干扰；堆大小应基于“峰值在途消息字节 × Java 表示膨胀系数 × 安全系数”实测，不凭 token 数估算。
- Java 21 先以 G1 为基线；用 JFR/GC log 比较分配率和 pause，再决定是否评估 ZGC。不要只凭平均暂停切换收集器。
- 关注大 `String`、`byte[]`、`MessageEnvelope`、事件类型字符串以及日志参数的分配热点。
- 避免在热路径创建临时集合、正则对象、完整 JSON 树和高基数标签。

### 10.3 P1：OkHttp 与连接

- 保持 `onMessage` 非阻塞，不在回调中执行数据库、远程调用、同步日志或完整业务计算。
- 显式监控 Dispatcher 线程、WebSocket 发送 `queueSize()`、PING/PONG 与连接代际，验证多连接下线程和连接池行为。
- 连接错峰建立、订阅批次加抖动、重连指数退避并设置全局重连并发上限，避免重连风暴。
- 比较文本帧与二进制帧路径；当前二进制回调的 `bytes.utf8()` 会创建字符串。只有在扫描与下游接口支持字节输入后，才可能消除此转换。

### 10.4 P1：队列与并发

- 保留有界队列和非阻塞 `offer()`，防止回调线程被业务处理反压锁死；生产环境需明确 drop 策略、告警与数据完整性要求。
- 依据实测峰值突发持续时间设置容量：`queueCapacity >= (λ_peak - μ_safe) × burstSeconds × safetyFactor`，前提是长期 `μ_safe > λ_sustained`。
- 当前消费者轮询所有连接队列，多连接时应测量空轮询与热点公平性；可对比“连接固定归属消费者”和“共享 MPSC 队列”，以吞吐、尾延迟和分配率选择，不预设结论。
- 若业务允许，对同 token 的可覆盖更新做合并；订单簿等要求完整顺序的事件不可盲目丢弃或重排。

### 10.5 P2：少拷贝/零拷贝

WebSocket、OkHttp 与 Java 字符串边界决定了严格“零拷贝”通常不可达，目标应是**少拷贝**：

- `book` 已在回调分类后不入业务队列，继续避免保存其原文、完整反序列化或日志输出。
- 非 `book` 若下游只需少数字段，采用流式扫描/解析，避免 `JsonNode`/POJO 全量构造。
- 评估让队列持有 `ByteString` 或紧凑字段对象，避免 `ByteString → String → POJO` 多份同时存活；必须先验证消息生命周期和内存占用。
- 避免 `substring`、拼接、正则和重复 UTF-8 长度计算造成额外扫描/分配。
- 不要为了复用可变缓冲区而破坏跨线程所有权；正确性优先于理论零拷贝。

### 10.6 P2：解析与对象分配

- 保持事件类型快速扫描，不对每帧做完整 Jackson 反序列化。
- 对顶层数组进行一次线性扫描，同时得到 event 数与必要类型；避免对每个字段重复 `indexOf` 全文扫描。
- event type 使用有限枚举/整数编码，避免为每条消息创建动态字符串和高基数 Map key。
- `MessageEnvelope` 仅保留下游必需字段；若不需要原始消息，解析后不应继续持有大字符串。
- 使用 JMH 做微基准、JFR 做真实负载分配画像；微基准结果不能替代端到端压测。

### 10.7 P2：日志与指标

- 热路径只累计计数，不逐帧打印；周期日志保持固定低频，并避免打印 payload。
- 对 close/failure/重连日志做速率限制，但首次异常和最终停止原因必须保留。
- Prometheus 标签禁止使用 asset ID 等高基数字段；逐连接标签在 32 条连接内可控，但仍需评估抓取开销。
- 指标快照采用增量窗口，避免每次构建大 Map、排序全部类型或扫描所有 token。

### 10.8 P3：资产加载与订阅规划

- 保留 `AssetIdLoader` 的线性 `joining` 实现，防止 O(n²) 拼接问题回归；218,634 ID 下将资产加载时间纳入启动指标。
- 订阅分片应预计算一次并按阶段取前缀/索引，避免每批次重复构造 `HashSet`、遍历最大目标资产和重建列表。
- 预生成或流式生成订阅 payload，控制单 payload 字节大小，并记录序列化时间与发送队列大小。

## 11. 建议生产架构

```text
                    ┌────────────── 控制面 ──────────────┐
                    │ asset目录/分片规划/代际/健康检查   │
                    │ 灰度升压/全局限速/熔断/重连协调    │
                    └────────────────┬───────────────────┘
                                     │
            ┌────────────────────────┼────────────────────────┐
            ▼                        ▼                        ▼
      WSS Worker 1              WSS Worker 2              WSS Worker N
   多连接、固定分片           多连接、固定分片           多连接、固定分片
   快速分类/序列校验          快速分类/序列校验          快速分类/序列校验
            │                        │                        │
            └─────────────── 有界分区事件总线 ──────────────┘
                                     │
                         无状态业务消费者/持久化层
                                     │
                         指标、告警、回放与审计存储
```

建议：

- 控制面维护 token → worker → connection 的确定性映射、订阅代际和期望状态，数据面只做低延迟接收与投递。
- worker 横向扩容，单 worker 保留 CPU、堆、网络和连接余量；不要把 200k 全部压在单进程/单连接上作为默认生产设计。
- 重连时按连接分片恢复，设置全局速率限制与随机抖动；避免所有 worker 同时全量重订阅。
- 业务处理与 WSS 接收隔离。若需要可靠不丢，应接入有明确容量和落盘语义的事件总线；内存队列的 `offer()` 丢弃只能用于明确接受数据损失的场景。
- `book` 不能服务端过滤，应单独计量带宽/CPU；如果业务不需要它，也要在最早的安全位置分类丢弃。

### 11.1 20 万 Token 的生产候选拓扑

在当前证据下，单连接 5,000 Token 已两轮稳定，单连接 10,000 Token 曾收到 `1013 slow consumer: send buffer full`，但尚不能解释为官方硬限制。因此初始生产候选以 **4,000—5,000 Token/连接** 设计：

| 方案 | 节点规格 | 数据连接/节点 | Token/连接 | 数据连接总数 | 正常节点数 | N+1 后节点数 | 适用判断 |
|---|---|---:|---:|---:|---:|---:|---|
| A | 2C2G | 4 | 5,000 | 40 | 10 | 11 | 成本最低候选，须证明 4 连接时 CPU/GC/网络仍有 40% 余量 |
| B | 2C4G | 8 | 5,000 | 40 | 5 | 6 | 推荐优先验证，故障域和运维成本较均衡 |
| C | 2C4G | 5 | 4,000 | 50 | 10 | 11 | 对热点/1013 更保守，连接数与心跳成本更高 |

连接总数只计数据连接；生产还应预留接管槽位，但备用节点在正常状态下不应重复订阅全部 Token。选型必须通过 24 小时有效高活跃窗口和单节点故障接管测试，不能只凭短时订阅成功。

### 11.2 快速恢复与防重连风暴

每条逻辑连接维护 `desired`（目标 Token）、`submitted`（本 generation 已成功进入 OkHttp 出站队列）和 `observed`（本 generation 已收到业务事件的 Token）三套状态。Polymarket Market WSS 没有公开的逐批订阅 ACK，因此 `WebSocket.send()==true` 只代表客户端入队，不能视为服务端确认。恢复完成应采用组合判据：所有批次已提交、应用层 PONG 正常、观察窗口内有业务事件；低活跃 Token 通过抽样 REST/订单簿或周期性重建连接校验，不能要求每个 Token 立即产生事件。

故障恢复状态机：

```text
OPEN/HEALTHY
  ├─ PONG 超时、连接失败、5xx、网络中断 → BACKOFF
  └─ 1013 slow consumer → SLOW_CONSUMER_COOLDOWN（更长冷却）
BACKOFF/COOLDOWN
  → 获取节点级重连许可（限制并发握手）
  → CONNECTING（generation + 1）
  → OPEN（稳定满 60s 后才清零失败退避）
  → 获取全局订阅令牌，分批恢复 desired
  → VERIFYING（PONG + 流量 + 抽样对账）
  → HEALTHY
```

恢复策略：

1. 普通网络失败采用指数退避 + full jitter；1013 使用更长基础冷却，避免立即重放造成同一缓冲再次打满。
2. 每节点限制并发 TCP/TLS 握手和总订阅批次/秒；整个集群还需控制面租约/令牌桶，避免 20 万 Token 同时重订阅。
3. 固定分片和 generation 防止旧连接回调污染新连接；重复失败的热点分片拆细或迁移到备用节点，而不是在原节点无限快速重试。
4. 无状态业务可接受断线窗口丢失时，RPO 明确为“断线期间事件可能丢失”；若需要订单簿正确性，重连后必须通过 REST snapshot/新的 book snapshot 建立基线后再接增量。
5. 建议目标：单连接故障 RTO p95 ≤ 60s，单节点故障 95% 分片恢复 ≤ 5min、100% ≤ 10min；具体 SLO 必须在受控故障演练中验证。

## 12. 容量模型

容量计算必须以实测流量为基础，而不是只按 token 数。

定义：

- `T`：总 token 数；
- `C`：连接数；
- `W`：worker 数；
- `r_f`：峰值 frames/s；`r_e`：峰值 events/s；`r_b`：峰值 bytes/s；
- `μ_cb`：单 worker 安全回调处理能力（frames/s）；
- `μ_ev`：单 worker 安全业务处理能力（events/s）；
- `B_net`：单 worker 可用下行带宽（bytes/s）；
- `H`：安全系数，建议由业务风险确定，例如 1.5—2.0；
- `L_conn`：实验验证的单连接安全 token 容量；注意它不是官方硬限制；
- `L_worker`：单 worker 安全连接数。

连接数下界：

```text
C >= ceil(T / L_conn)
```

worker 数取各资源约束的最大值：

```text
W >= max(
  ceil(H × r_f / μ_cb),
  ceil(H × r_e / μ_ev),
  ceil(H × r_b / B_net),
  ceil(C / L_worker)
)
```

队列容量用于吸收突发：

```text
Q >= H × max(0, λ_peak - μ_safe) × burstSeconds
```

稳态必要条件：

```text
μ_safe > λ_sustained
```

带宽预算必须包含 `book`：

```text
B_required = H × (book_bytes_per_sec + non_book_bytes_per_sec + protocol_overhead)
```

生产选型以多轮测试中最差的有效高活跃窗口为输入，并采用 PASS 容量再折减，不使用“首个 FAIL 前一级”直接作为生产容量。还应预留一台/一个分片故障后的接管余量，即 N+1 或按故障域规划。

## 13. 风险与合规提醒

- 本方案面向容量验证，不用于规避平台限制或制造拒绝服务。测试前应确认适用的服务条款、接口政策和组织授权。
- 使用逐级升压、连接/订阅限速、自动停止和受控时段，避免影响平台及其他用户。
- 不公开或传播可能包含账户标识、鉴权信息或敏感业务数据的 payload、日志和抓包。
- 若平台提供正式容量说明或支持渠道，应优先申请确认；实验观测不能替代官方承诺。
- 发现异常服务端压力迹象时应主动降载并保留证据，措辞保持为“观测”或“候选限制”。

## 15. 最终决策规则

1. 选择满足业务总 token、峰值 `bytes/s` 和 `events/s` 的最小连接/worker 组合，而不是追求单连接数字最大化。
2. 生产容量必须在至少 3 轮高活跃有效窗口中 PASS，并保留故障接管和峰值安全系数。
3. 任一结果若缺少 event 量纲、主机资源或网络证据，只能作阶段性参考。
4. 单连接异常、多连接恢复，只能证明分片改善了该实验条件下的表现；在没有官方说明前，不定义为服务端硬限制。
5. 优先消除客户端可证实的 O(n²)、重复解析、过量分配、同步日志和队列积压，再讨论服务端限制。
